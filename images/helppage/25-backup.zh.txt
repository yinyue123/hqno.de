title: 备份
summary: 备份存到哪、存什么、保留几份，以及怎么把数据拿回来

这台容器的磁盘，不是这台容器的备份。跟着机器一起死掉的副本没有复制任何东西，
而磁盘正是真正会坏的那个部件。所以这件事的形状是：先找一个不在这台机器上的地
方，再说清楚要存什么，然后让它每天晚上自己跑。

下面说的都在 `app-setup` 的「备份」标签页里，就在「数据库」旁边。

== 第一步：先有个存放的地方 ==

标签页上面那一排是存储源，一种一张卡。挑你手上有的那个：

    S3        AWS、MinIO、阿里云 OSS、腾讯云 COS、B2
    R2        Cloudflare R2
    WebDAV    Nextcloud、ownCloud、群晖、坚果云
    FTP       便宜主机一般都会给你一个
    rsync     一台 NAS，或者另一台你自己的机器，走 SSH
    SCP       只有 sshd、没有 rsync 的那种存储盒子

打开一张，填好，按「测试连接」。这一步不是走过场：它会建一个目录、往里写一个
小文件、再读回来比对字节、然后删掉。只能上传不能列目录的凭据，以及能往给你的
目录里写文件、却不能在它下面建子目录的账号，这两种都很常见，而且在第一次备份
真正跑起来之前都看着一切正常。

S3 那一类的 endpoint 就是你的服务商后台给你的那个：

    R2     https://<账号id>.r2.cloudflarestorage.com
    B2     https://s3.us-west-000.backblazeb2.com
    OSS    https://oss-cn-hangzhou.aliyuncs.com
    COS    https://cos.ap-guangzhou.myqcloud.com
    MinIO  https://minio.example.com

rsync 和 SCP 不用填密码。按「显示公钥」，把打印出来的那一行加到对面机器的
`~/.ssh/authorized_keys` 里，然后再测试。

== 第二步：说清楚要备份什么 ==

下面那一排是备份任务：MySQL/MariaDB、PostgreSQL、Redis、MongoDB，还有一个
「文件和目录」，用来管那些没有专门卡片的东西。

打开任意一张，它已经知道这台机器上那个数据库的情况了 —— 端口、安装时生成的
账号密码都替你填好了。只有当数据库不在这台机器上时才需要改；一个任务完全可以
去备份另一台主机上的服务器。

唯一必须你自己选的是「目的地」。没有目的地的任务会拒绝安装并且告诉你原因，而
不是每天晚上老老实实往同一块磁盘上的一个目录里写。

每个任务在目的地上有自己的目录，用这台机器的名字打头：

    s3://你的桶/backups/web01/backup-mysql/
                        ^^^^^^^^^^^^^^^^^^
                        第一次备份时自动建好

没有明确理由就别改它。机器名正是用来防止两台共用一个桶的容器互删对方历史的。

== 数据库的三种拷法 ==

    dump   自己一边跑一边导出。什么都不停，站点不断。
           默认值，通常也是对的答案。
    binary 用数据库自带的工具做物理拷贝，同样不停服务。
           你要的就是数据目录本身时用它。
    files  停服务 → 拷数据目录 → 再起来。这是从正在运行
           的库底下拷文件的唯一诚实做法，代价是那段停机。

每天晚上做一次 `files` 备份，等于每天晚上让站点停一次，而且换不来任何好处。
除非你要搬机器，否则就用 `dump`。

== 保留几份 ==

不是「最近 7 份」。是四个数字，每一个都保留对应时间段里最新的那一份：

    每小时保留   0     除非你一天备份不止一次，否则关着
    每天保留     7
    每周保留     4
    每月保留     6

按每天备份算，这是 14 个文件，覆盖一年多：最近七天各一份，往前一个月里每周
一份，再往前半年里每月一份。旧的不是按个数删掉的，是被逐级稀释掉的 —— 一份
备份变旧的过程，是先不再是当天那份、再不再是当周那份、再不再是当月那份，然后
才轮到它。

设之前先拿一份档案的大小乘一乘这几个数。小容器上，一个大库的十四份是放不下的。

有个容易踩的地方：「每天保留 7」数的是天，不是文件数。如果你是每周备份，那七
天之内最多只会有一份备份，剩下的靠周和月这两级去撑。这是对的，但确实出乎很多
人意料。

== 怎么把数据拿回来 ==

每个任务上有三个按钮：

    ▤ 列出所有备份   这里和目的地上各有哪些，带日期
    ✓ 校验           下载一份看它能不能打开。完全不碰数
                     据库，线上机器也可以随便按
    ⟲ 恢复           把它放回去。会先问一句，并说明要
                     覆盖的是什么

不在「设置 → 哪一份」里填名字的话，恢复取的是最新那份。它先在本机找，本机没
有就从目的地下载 —— 所以一台换过磁盘的容器照样能恢复，这也正是整件事的意义。

在一台刚重装过的容器上，一共四步：

    app-setup install backup-mysql     MariaDB 没了会一并装
    app-setup set backup-mysql store=s3 folder=web01/backup-mysql
    app-setup list backup-mysql        能看到你的备份吗
    app-setup restore backup-mysql

`/data` 能扛过重装，你的设置不能，所以才有前两步。

== 在脚本里用 ==

    app-setup backup backup-mysql      立刻跑一次
    app-setup restore backup-mysql     最新那份
    app-setup list backup-mysql        有哪些
    app-setup set backup-mysql schedule=daily keep_daily=7

    sh /etc/app-setup/backup-mysql.sh restore backup-mysql_20260813041700.tgz

最后这条是在 shell 里恢复某一份指定档案的写法。

== 要紧的几句 ==

两个地方，不是一个。本地那份是给你上午十点发现迁移搞坏了、要马上回滚用的；异
地那份是真出事时救你的。这是两件不同的事。

别都放在同一家公司。桶开在那个也管着你域名的账号下面，一次密码重置就能让它跟
别的东西一起消失。

配好那天就跑一次。按「立即备份」，看着它跑完。测试连接证明的是凭据，只有跑完
一次备份才能证明备份。

然后专门恢复一次。恢复到一台不要紧的容器里，或者一个你专门建的库里。没人恢复
过的备份只是个念想，而这一步是所有人都会跳过的那一步。

密钥只给一个桶。凭据就放在这台机器的一个文件里。申请它的时候只授权一个桶、一
个目录，别用整个账号的权限。

把它存到哪写下来。桶名、目录、用的哪种存储源 —— 写在这台容器之外的地方。恢复
是从「知道去哪儿找」开始的，而知道的那台机器，正是已经没了的那台。
